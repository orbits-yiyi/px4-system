# PX4 系统学习路线

[文档首页](README.md) · [系统架构与技术原理](TECHNICAL.md) · [代码架构与开发指南](DEVELOPMENT.md) · [操作与调试手册](OPERATIONS.md)

目标是能够独立理解、使用、分析、修改和验证 PX4，并将方法迁移到新需求。路线从零建立系统认识，不假设已经安装环境、完成飞行或读过源码。四旋翼承担第一条完整学习链，固定翼、VTOL、车辆和硬件用于检查理解能否迁移。

## 1. 最终要形成什么能力

“掌握 PX4”应能通过下面的工作检验。读完文章、运行过命令或记住参数名，只能作为过程证据。

| 能力 | 独立完成的工作 | 合格证据 |
|---|---|---|
| 系统设计 | 把一个任务分解为硬件、估计、控制、导航、管理和外部应用职责 | 系统图、接口与约束，能解释异常时的行为 |
| 配置与运行 | 从干净源码和明确环境恢复系统，配置机型、任务与保护 | 可复现的构建、参数、任务及运行记录 |
| 原理分析 | 用坐标、模型、时序、状态机解释实际现象 | 预测与数据对照，说明支持和不支持的结论 |
| 代码开发 | 找到正确修改层，处理构建、调度、接口和生命周期 | 有边界的实现、相关测试、集成验证和恢复方式 |
| 故障定位 | 区分输入、估计、目标、控制、执行、通信与资源问题 | 最小复现、证据链、根因与回归用例 |
| 迁移与集成 | 接入新设备/应用或研究另一机型 | 哪些假设保持、哪些改变，以及相应验证 |

通用能力达到后，再选择估计、控制、平台或自主应用深入研究。不要求背熟全部驱动寄存器或证明所有算法，但遇到陌生功能时，要能找准职责、读懂契约、构造实验、判断结果。

## 2. 如何安排学习

### 2.1 一条主线，三次能力提升

```text
阶段 1～3：认识系统，建立物理语言，能独立构建和调试
    ↓
阶段 4～7：从测量到任务，能解释闭环和异常行为
    ↓
阶段 8～10：实现应用与内部改动，完成部署/迁移和综合验证
```

| 阶段 | 核心问题 | 必须留下的成果 |
|---|---|---|
| 1 整体架构 | PX4 在完整载具中负责什么 | 系统图与任务生命周期 |
| 2 飞行基础 | 消息中的量代表什么，运动有什么约束 | 坐标、力、时间和反馈的计算与解释 |
| 3 代码工程 | 功能如何编入、启动、运行和调试 | 模块卡片、一次完整改动与调试记录 |
| 4 测量系统 | 物理量如何变成可信输入 | IMU 双路径与设备误差预算 |
| 5 状态估计 | 状态来自哪里，什么时候不可信 | 融合路径、退化/重置分析与测试 |
| 6 控制执行 | 目标如何变成实际作用 | 控制链图、响应比较与分配分析 |
| 7 导航安全 | 任务如何推进，异常后如何选择行为 | 任务方案、状态机与场景验证 |
| 8 通信应用 | 外部程序怎样正确参与系统 | 接口契约、可恢复应用与断流验证 |
| 9 硬件机型 | 软件怎样落实到设备与不同载具 | 资源/配置表、部署或迁移报告 |
| 10 综合开发 | 新需求怎样成为有证据的实现 | 系统应用、内部改动及部署/迁移成果 |

先按顺序打通一次，再选专题加深。阶段 3 只要求建立工程方法，阶段 5 再进入 EKF 数学和测试，阶段 6 再进入控制细节。不要第一周同时安装所有仿真器、接 ROS、移植硬件和修改控制器。

### 2.2 基础薄弱时怎样补

| 自测问题 | 暴露的缺口 | 补足方式与回归点 |
|---|---|---|
| 机头转东后，机体前向速度在 NED 中是什么 | 向量与旋转 | 做阶段 2 的坐标题，再解释一个实际消息 |
| 静止加速度计为什么不为零 | 比力与重力 | 从刚体模型推演，再与测量章节对照 |
| 不知道类成员何时初始化/销毁 | C++ 对象与生命周期 | 读 WorkItem 构造、Run、退出；先用小程序理解相同语法 |
| 不理解线程、回调和阻塞区别 | 操作系统基础 | 画阶段 3 的执行图，说明共享队列被阻塞的后果 |
| 协方差为什么有非对角项 | 概率与线性代数 | 先做标量更新，再做位置/速度两状态模型 |
| 能运行 make，却不知道用了哪些代码 | 构建依赖 | 追踪 Kconfig、模块 CMake、编译数据库和最终符号 |

每次补足一个明确缺口后立即回到 PX4 例子验证。数学和 C++ 可以并行补课，不必等“所有基础学完”才开始系统认识。

### 2.3 每次学习如何推进

建议以能集中完成的一段工作为单位，例如 2～3 小时：先写一个问题和预测，读相关原理及实现，完成一个最小实验，最后解释结果并记录未解决项。每周留一次回顾，把局部知识重新放回系统图。

时间安排应随基础调整：完整系统学习通常需要持续数月，涉及板级开发和实际飞行时还取决于设备与试验机会。下面用能力门槛决定推进，不以“第几天必须学完 EKF”替代理解。

每阶段只需要一份有内容的记录，包含问题、关键机制、操作、证据、结论和限制。无需增加打卡系统或为每条命令建立文档。优先完成阶段中的基础工作，再做迁移题；深入项目放到阶段 10。

<a id="milestones"></a>
### 2.4 用三次综合验收决定是否继续

阶段内的练习允许照步骤完成，下面的验收需要自己组织操作；可以查源码和参考资料，但要先写判断和方案，再动手。这样检验的是知识能否组合使用。

| 验收时机 | 独立任务 | 可以进入下一段的依据 |
|---|---|---|
| 阶段 3 结束 | 为独立教学模块增加状态字段，完成生成、发布、读取和记录；解释一次停止/重启 | 找得到所有修改点，能区别构建、运行与记录问题；同伴可按记录复现 |
| 阶段 7 结束 | 用一次任务的配置、源码和日志，区分目标受限、估计变化和控制跟踪问题；解释一个取消或退化过程 | 有同时间轴的目标/反馈/模式证据，能排除至少一个其他解释，而不是只凭曲线形状猜测 |
| 阶段 10 结束 | 完成需求未给出实现位置的系统应用、内部改动与部署/迁移，并处理一个新失败 | 设计有边界、实现有回归、异常有恢复、结论有适用条件，能从干净源码和记录恢复软件结果 |

验收失败时回到对应责任层补足：找不到文件补阶段 3，分不清信号补阶段 2/4，解释不了有效性补阶段 5，分不清目标与跟踪补阶段 6，不能解释模式选择补阶段 7。不要把重做整套环境作为通用补救。

软件主线完成后，可以判断已经具备 PX4 软件分析与开发的系统方法。硬件集成、板上实时性能与真实闭环需要阶段 9 的相应实测成果；只做仿真时，将这些能力标为待完成。后续专题深化也以能完成具体任务为依据。

## 阶段 1：建立整体架构与任务视角

**进入条件**：无 PX4 前置经验。

**目标**：能从一个完整任务解释系统组成、数据闭环、控制权与生命周期。先形成整体，再讨论哪个工具或模块。

**阅读**：[系统架构第 1 章](TECHNICAL.md#c1)，再浏览[硬件组成](TECHNICAL.md#c3)；暂不展开 EKF 和 PID 公式。操作入口：[系统建模](OPERATIONS.md#s1)。

**按顺序完成**：

1. 以“起飞、访问两个观察点、拍摄、返回、降落”为任务，列出载具、飞控、传感器、动力、地面站、伴随计算机和载荷。对每项写出输入、输出、是否必需。
2. 画物理闭环，再画 PX4 内部的测量、估计、管理、导航、控制、分配和服务。把地面站的命令放到图中，说明它与传感器反馈的区别。
3. 写任务生命周期：准备、激活、运行、人工取消、异常、结束。每一步标注由谁决策、由谁执行、如何确认完成。
4. 推演“地面站断开”和“位置观测丢失”。只列出需要进一步查明的条件，不背诵某个固定保护动作。

**成果与通过标准**：一张系统图和一份生命周期表。能够解释 PX4、Pixhawk、NuttX、QGC、Gazebo、ROS 的不同职责；能够区分姿态、位置、目标、模式、解锁和任务进度；能将“增加视觉定位”和“增加相机任务”分配到不同接口。

**卡住时**：如果所有问题都指向“控制器”，回到第 1 章逐个补上测量、控制权和业务职责。此阶段不用靠运行命令弥补架构缺口。

**迁移题**：把巡检换成室内定位任务，说明系统图中哪些信息源与返回条件改变，哪些闭环仍保留。

<a id="s2"></a>
## 阶段 2：建立物理、数学和数据语义

**进入条件**：能区分状态、目标与执行器作用。

**目标**：读一个消息或公式时，能判断坐标、单位、时间、参考和有效性；能识别不可能的运动请求。

**阅读**：[飞行原理与基础数学](TECHNICAL.md#c2)。操作入口：[计算与模型推演](OPERATIONS.md#s2)。

**按顺序完成**：

1. 完成 NED/ENU 与 FRD/FLU 向量换算，画出机头向北和向东时的机体轴。说明姿态变换为什么不能随意交换四元数分量。
2. 计算地面 z=-0.5 m、空中 z=-3.5 m 时的相对上升量，分别解释局部高度、离地高度、Home 高度和海拔。
3. 推导静止加速度计的比力、四旋翼倾斜 30° 保高的推力需求、惯性积分中常值偏置的误差增长。
4. 计算有限减速度下的停止距离，再加入时延讨论模型为何低估实际停止距离。
5. 为 `VehicleLocalPosition` 和 `TrajectorySetpoint` 各选三个字段，说明时间、NaN/有效性和参考重置的语义。

**成果与通过标准**：保留带单位的计算过程及一张数据契约表。必须能解释“姿态固定但角速度为零”“位置更新但无效”“曲线更平滑却增加延迟”“目标值为 NaN 有时是正确接口”。

**卡住时**：先缩到一维位置/速度模型，再回到三维；先用轴向旋转，再读四元数。不能用“坐标转换函数会处理”替代对方向的理解。

**迁移题**：外部视觉把向上为正的位置送入 NED 接口但没有转换，会在哪些层产生怎样的错误？设计一个无需起飞即可识别该问题的检查。

<a id="s3"></a>
## 阶段 3：建立完整代码开发闭环

**进入条件**：能读基础 C++ 类和函数，理解阶段 2 的数据约定；开发环境按附录准备。

**目标**：独立完成“找到实现 → 确认构建与启动 → 修改 → 编译 → 运行 → 调试 → 验证”。这是所有后续阶段持续使用的能力。

**阅读**：[开发指南第 1～6 章](DEVELOPMENT.md#d1)，随后读[模块地图与三条实现路径](DEVELOPMENT.md#d7)。操作入口：[工程实践](OPERATIONS.md#s3)、[环境准备](OPERATIONS.md#environment)。

**按顺序完成**：

1. 核对源码、分支、子模块、镜像和挂载路径。完成 SITL 构建，识别二进制、生成头、编译数据库和 rootfs，解释每种产物的作用。
2. 配置编辑器索引，沿 `work_item_example` 的 Kconfig、CMake、类定义、入口和调度阅读，画出构建图与运行图。启动、停止并确认消息时间变化。
3. 完成[参数驱动模块练习](DEVELOPMENT.md#d9)：定义周期参数、更新调度、发布计数、验证停止/重启。随后整理为独立模块，并完成[自定义消息](DEVELOPMENT.md#message-exercise)的生成、运行和记录。先预测频率，再观测；保留全部改动差异。
4. 用单元测试进入 GDB，检查一次算法调用的输入和调用栈；再在 SITL 中断到 WorkItem，区分模块类、工作队列线程和主进程。
5. 将相同方法应用到 `mc_pos_control`，找到状态输入、轨迹输入、模式条件、参数、算法库和输出。不要求此时改控制算法。

**成果与通过标准**：一张真实模块卡片、一项有限改动、一份调试记录。能解释“文件存在但未编入”“编入但未启动”“启动但没有新输入”“参数已保存但行为未更新”四种情况；能只重建相关目标并恢复实验配置。

**卡住时**：构建错误先查首条错误和路径；编辑器错误先查编译数据库；断点错误先查二进制、符号和执行路径。不要每遇到问题就清空仓库或重新拉依赖。

**迁移题**：把示例作为原型，说明独立模块需要改变哪些注册点，为什么新增一个 `.cpp` 不能自动得到新 Shell 命令。

<a id="s4"></a>
## 阶段 4：理解测量、驱动和传感器处理

**进入条件**：能追踪发布/订阅和模块触发；知道比力、角速度和积分量的区别。

**目标**：从物理设备追踪到算法输入，区分安装、设备、换算、时间、滤波和估计问题。

**阅读**：[硬件系统](TECHNICAL.md#c3)、[测量处理](TECHNICAL.md#c5)、[IMU 实现路径](DEVELOPMENT.md#d8)。操作入口：[测量实践](OPERATIONS.md#s4)。

**按顺序完成**：

1. 为陀螺仪、加速度计、GNSS、气压和距离传感器列出直接观测、主要误差、采样与延迟条件，不把估计输出写成设备直接测量。
2. 读 BMI088 状态机和 FIFO 处理，追踪物理单位、样本时间、device_id 及消息发布。指出初始化失败、读失败、无新数据的不同处理。
3. 画 IMU 分流图：一条形成估计器的运动增量，一条形成角速度控制输入。标注校准、偏置、积分和滤波的位置。
4. 用仿真数据对照静止、旋转、运动三个阶段，解释信号意义。有设备时再按台架流程校准、检查方向和设备错误。
5. 为一个新传感器写集成条件：总线、量程、方向、时间、消息、异常恢复和验证方式。

**成果与通过标准**：双路径图、驱动状态机与误差表。能解释“SPI 读通但数据不能用”“消息存在但不是选中的实例”“提高采样率未降低控制延迟”；能说明仿真没有覆盖哪些电气与机械问题。

**卡住时**：先只追一个轴、一个设备实例和一个时间戳；确认基础链后再分析冗余。若信号单位不清楚，暂不讨论滤波参数。

**迁移题**：IMU FIFO 时间错位与气压慢漂移会怎样以不同方式影响估计？为两者选择不同证据。

<a id="s5"></a>
## 阶段 5：理解估计原理及信息源管理

**进入条件**：具备协方差和线性化的基础，能解释测量时刻与处理时刻。

**目标**：分析状态如何得到、何时退化、为何重置；能够把数学融合与模式可用性连接起来。

**阅读**：[状态估计](TECHNICAL.md#c6)，对照[模块职责](DEVELOPMENT.md#d7)。操作入口：[估计实践](OPERATIONS.md#s5)、[回放方法](OPERATIONS.md#e4)。

**按顺序完成**：

1. 手算标量卡尔曼更新，改变预测或观测方差，解释结果变化；再对位置/速度模型画状态相关性。
2. 列出姿态、航向、高度、水平位置分别由哪些观测约束，推演一项观测失去后的剩余能力。
3. 沿 GNSS 高度路径追踪样本输入、缓冲、质量检查、融合条件、创新、超时与重置，最后追到 `vehicle_local_position`。
4. 运行高度融合测试，用确定的扰动解释一个拒绝或参考切换行为；检查断言到底证明什么。
5. 分析一段日志的估计变化，联合位置、速度、有效性、reset counter、创新和模式判定原因。有符合记录要求的日志时，再做一次相同输入下的 EKF 回放比较。

**成果与通过标准**：融合状态图、一个可控测试分析、一条有时间依据的退化/恢复说明。能区分数值输出、成功融合、状态有效、模式可执行；没有独立真值时，不把平滑度当定位精度。

**卡住时**：先研究一个标量观测及其条件，再扩展全状态。遇到重置先查参考和计数，不通过增加 PID 或放宽所有创新门限掩盖问题。

**迁移题**：给外部视觉设计观测契约，说明坐标、时间、协方差、重定位与失联分别需要怎样处理。

<a id="s6"></a>
## 阶段 6：理解控制链、分配和性能取舍

**进入条件**：能解释有效状态与测量延迟，能运行算法测试并分析日志。

**目标**：从目标到执行器贯通闭环，分辨轨迹限制、控制误差、估计问题和执行器能力不足。

**阅读**：[控制与执行器分配](TECHNICAL.md#c7)、[核心代码路径](DEVELOPMENT.md#d8)。操作入口：[控制实践](OPERATIONS.md#s6)。

**按顺序完成**：

1. 从角速度内环向外读 RateControl、AttitudeControl、PositionControl，逐层记录输入、输出、单位、状态和限制。手算一轮非零 P/I/D/FF。
2. 用已有测试研究姿态方向、推力/倾角限制和积分饱和；再完成[算法库与测试练习](DEVELOPMENT.md#algorithm-exercise)，自己定义行为、注册测试、验证正常与错误输入。明确纯算法与模块门控的分界。
3. 在仿真中建立基线，记录轨迹、内部目标和实际状态。先改变一个轨迹限制，判断变化来自目标计划还是跟踪能力。
4. 对相同场景比较响应时间、误差、噪声、饱和与模式条件。若进入增益实验，先恢复基线，只改变一个参数，并保留恢复值。
5. 沿整体力矩/推力、分配器、逻辑执行器和物理输出追踪；用几何解释控制有效性矩阵，说明某方向无法实现时怎样反馈。

**成果与通过标准**：控制链图、一个有明确窗口的对照实验、执行器映射说明。能够解释“目标没变快”“目标变快但跟不上”“估计跳变”“输出饱和”的不同证据；不把归一化推力直接当 Newton 或 PWM。

**卡住时**：将外环问题拆到其直接下游，先确认目标与反馈同坐标、同时间，再看误差与限制。没有可信基线时不连续调整多个增益。

**迁移题**：质量增加或电机响应变慢时，哪些物理假设、限制和控制性能需要重评？哪些变化不是重新算一组 PID 就能解决？

<a id="s7"></a>
## 阶段 7：掌握任务、模式和安全行为

**进入条件**：能解释闭环、状态有效性和物理约束。

**目标**：设计完整自动任务，理解控制权交接和故障仲裁，能解释系统为何进入某个行为。

**阅读**：[导航任务](TECHNICAL.md#c8)、[管理安全](TECHNICAL.md#c9)、[航点实现路径](DEVELOPMENT.md#d8)。操作入口：[任务规划与场景验证](OPERATIONS.md#s7)。

**按顺序完成**：

1. 在纸面设计一项起飞、访问、停留、返回和降落任务，明确坐标、高度参考、转弯/停止空间、能量与人工取消方式。
2. 使用 QGC 规划、上传、下载核对，再在仿真执行。将任务项进度、导航目标、轨迹与实际运动放在同一时间线上。
3. 阅读 Mission 到达判断和 RTL 选项，解释接受半径、路径误差和最终保持误差的差异。
4. 分别验证正常完成、中途切换/取消、一次有明确支持路径的退化条件。实验前记录预期动作和关键参数，实验后核对实际模式及原因。
5. 建立位置有效性、输入链路和能量条件的场景矩阵；选一个保护功能测试，阅读其状态转换与恢复断言。

**成果与通过标准**：任务文件、场景表与行为时间线。能区分命令接受和动作完成、用户意图和实际模式、异常检测和动作仲裁；解释相同故障为何可能在不同模式下采取不同动作。

**卡住时**：先分开命令、实际模式、导航目标和输出许可，再定位哪个阶段没有成立。不要用强制解锁或一揽子关闭检查来让实验表面成功。

**迁移题**：任务结束前 GNSS 恢复，是否立即继续原任务？列出必须查看的状态和恢复规则，不能只回答“有 GPS 就可以”。

<a id="s8"></a>
## 阶段 8：开发可恢复的外部应用

**进入条件**：理解模式、超时、任务与目标的区别；能读写一种应用语言。

**目标**：把外部应用做成有接口契约和失败出口的系统组成，能够定位传输、协议和行为层问题。

**阅读**：[通信与应用集成](TECHNICAL.md#c10)、[Offboard 实现路径](DEVELOPMENT.md#d8)。操作入口：[通信实践](OPERATIONS.md#s8)。

**按顺序完成**：

1. 先写接口表：谁发布什么、坐标/单位、频率、采样时间、有效性、确认和超时。选择 MAVLink 作为第一次接入，先不同时增加 ROS 环境变量。
2. 建立只读遥测，核对 system/component、端口方向与飞控状态；用一个可确认请求学习 ACK 与实际状态的区别。
3. 在仿真中运行保持实验，记录预发送、请求模式、确认、持续目标和正常退出的状态转换，再验证断流。
4. 将示例重构成显式状态机：连接、等待条件、请求控制权、执行、退出、失败；为拒绝进入、丢包和重连规定处理。
5. 再研究 DDS 路径，核对选题、消息版本与 QoS。需要 ROS 时完成对应实验；外部视觉或载荷另按观测/动作接口验证，不能把它们混成目标流。

**成果与通过标准**：能运行的仿真应用、接口说明和两条异常证据。程序要确认行为、超时退出、保留日志；不能仅以 send 无异常或 topic list 有名字判定成功。

**卡住时**：按传输 → 身份 → 消息契约 → 飞控状态排查。不要一边换网络模式，一边换消息版本和控制层级。

**迁移题**：从位置目标改为角速度目标，哪些控制职责转移到外部程序？应增加哪些状态、时序与失效验证？

<a id="s9"></a>
## 阶段 9：连接真实硬件并比较其他机型

**进入条件**：能够解释传感器、输出映射和安全条件；已建立配置/日志保存习惯。

**目标**：理解平台和物理能力的限制，形成板上开发方法；能够把已有知识迁移到不同动力学。

**阅读**：[硬件架构](TECHNICAL.md#c3)、[机型体系](TECHNICAL.md#c11)、[驱动和平台开发](DEVELOPMENT.md#d10)。操作入口：[硬件实践](OPERATIONS.md#s9)、[板上调试](OPERATIONS.md#e8)。

**按顺序完成**：

1. 选择一块具体板卡，建立 MCU、内存、启动、总线、传感器、电源、串口、输出和调试接口表。只写真实型号和已确认资源。
2. 选择匹配目标交叉编译，保留 ELF、固件包、参数及源码身份；说明引导程序、固件和机型参数的不同作用。
3. 有设备时按无桨台架流程检查启动、方向、校准、通信、输出和资源，再进入满足试验条件的后续验证。无设备时完成设计与源码研究，并把实测能力保留为未完成项。
4. 学会系统控制台、MAVLink Shell、SWD/GDB 和 HardFault 的适用范围；能够根据启动失败阶段选择入口。
5. 深入一种其他机型：固定翼研究空速/能量/路径，VTOL 研究过渡状态与失败回退，车辆研究曲率及驱动约束。对照其启动和控制模块，重画功能链。

**成果与通过标准**：资源与配置表、匹配的产物记录、部署证据或待验证清单，以及另一机型的差异分析。能说明 SITL 的哪些结论可迁移、哪些需要板上测量；不能把硬件实测缺口标为已掌握。

**卡住时**：从供电、启动控制台和设备身份向上定位；没有稳定启动前不改上层控制。跨机型时从运动能力与目标含义重新建立假设。

**迁移题**：固定翼 Hold 为什么不能用四旋翼原地悬停验收？它会怎样改变围栏、能量和返航任务设计？

<a id="s10"></a>
## 阶段 10：以三个工程成果证明独立能力

**进入条件**：前述阶段能独立复现主要实验，并解释结果与限制。

**目标**：在未给出逐条答案的需求下，自己组织系统、实现、调试与验证。

**阅读**：[系统配置与工程组织](TECHNICAL.md#c12)、[开发验证](TECHNICAL.md#c13)、[不同功能的开发方法](DEVELOPMENT.md#d10)。操作入口：[综合项目](OPERATIONS.md#s10)。

### 项目 A：完整任务应用

实现“访问两个观察点并停留、允许取消、失败后退出至明确行为”的仿真应用。先提交自己的设计说明：任务状态、目标层级、进入条件、控制权、完成判断、断流和重连处理；然后实现。

验收至少覆盖正常完成、开始条件不足、人工取消、目标流中断四条路径。用应用记录、飞控模式、目标、反馈及事件证明行为。若加入相机，分别证明飞行到达、触发接受和实际载荷反馈；纯仿真缺少的设备证据应标明。

### 项目 B：一项有实际行为影响的 PX4 内部改动

建议从轨迹限制、数据有效性处理或设备异常恢复中选一个明确需求。先说明现有实现在哪里、为什么不满足需求、应改变哪一层、有哪些消费者；避免直接以“增加一段代码”为目标。

先构造能揭示原问题的测试或场景，再实现，覆盖正常、边界、异常、恢复；最后用仿真检查集成及资源影响。教学 WorkItem 可以作为原型，但最终项目还需证明真实需求、设计取舍和回归。

### 项目 C：设备部署或机型迁移

有硬件时完成一套设备配置与台架验证，保留对应固件、参数、连接、调试和日志；具备实际试验条件后补充闭环证据。暂无硬件时完成一种其他机型的仿真任务、控制与保护分析，并明确缺少实物验证。

三项成果不必各建复杂仓库；可以放在同一个学习仓库的工作分支中。提交应按可解释的功能组织，先审查源码差异和产物边界，再保存需要版本化的内容。

### 最终评审问题

| 问题 | 必须给出的回答 |
|---|---|
| 为什么这样分工 | 功能边界、控制层级与资源条件 |
| 为什么放在这段代码 | 构建、启动、触发、输入输出及消费者 |
| 为什么认为结果正确 | 对照条件、指标、测试与运行证据 |
| 失败会发生什么 | 检测、动作、超时、恢复和人工接管 |
| 哪些结论尚未验证 | 模型、环境、平台和设备边界 |
| 别人如何复现与恢复 | 源码/依赖、环境、参数、任务、步骤与恢复方法 |

能在不依赖逐条指导的情况下完成这些回答，并处理一个新出现的失败，才达到本路线的独立开发目标。

## 3. 完成主线后怎样继续深化

| 深入方向 | 建议研究问题 | 可检验成果 |
|---|---|---|
| 估计 | 多源时间对齐、可观测性、观测失配、状态重置 | 新观测或算法改动、回放与真值对照 |
| 控制 | 时延、系统辨识、饱和、分配和不同动力学 | 模型、控制设计及一致工况下的性能比较 |
| 平台 | 总线/驱动、队列、内存、启动和板级适配 | 稳定设备接入、资源预算与板上故障证据 |
| 自主应用 | 任务状态机、规划、视觉、载荷和控制权 | 完整任务及异常恢复的系统验证 |

选择一个方向持续深入，同时保留系统评审习惯。一个估计改动要考虑控制与模式，一个通信改动要考虑时效与权限，一个驱动改动要考虑单位、时间和资源。能保持这种跨层判断，才会逐渐形成对 PX4 的熟悉与掌控。

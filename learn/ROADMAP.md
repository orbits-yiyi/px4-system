本路线把“系统掌握 PX4”落实为按依赖排列的工程任务：认识系统边界，解释源码怎样变成程序，理解运行和数据机制，研究测量、估计、控制与任务，完成外部集成、故障定位、硬件部署和跨机型开发。阅读、操作和验收组成同一项任务。

路线提供从零开始的入口，也允许从已经具备的能力进入。具体接口以当前仓库为准，版本、镜像和路径统一查[环境约定](OPERATIONS.md#environment)。

**已经能启动仿真、读取数据，但仍无法独立分析或修改时，从[贯通课：位置控制为何启动、何时真正执行](#working-through-position-control)开始。** 这节课直接讲一个实际飞行模块，把启动脚本、调度、消息、模式条件、算法与输出连起来；后面的十个阶段用于补全系统能力。环境入门和教学数值示例可按需要回查。

**第一次接触 PX4，先读[从零系统导读第 1～4 章](SYSTEM_GUIDE.md#system)，认识整机、仿真与控制闭环；再进入[第一课：读懂一个 PX4 模块的工程结构](#lesson-1-1)。** 第一课给出实际代码、逐项解释和参考答案。总路线用于查看后续方向，入口自测用于学后检查；开始时不需要先完成全部自测、整理环境报告或自行画架构图。

<a id="mastery"></a>
## 已经会运行以后，怎样检验自己掌握了系统

“系统掌握”需要覆盖全系统，也需要具备深入一个陌生模块的能力。当前的目标是：给出一个需求或故障，能判断它属于哪一层，找到相关接口和代码，解释执行条件，完成改动，并用实验判断结果。仅熟悉启动命令或完成某个示例，尚不能证明这些能力。

下面三种关系要分开理解，然后再对应起来：

| 关系 | 回答的问题 | 应留下的证据 |
|---|---|---|
| 构建与启动关系 | 哪些代码编进来，本次又选择启动了哪些功能 | 构建配置、实际启动入口、机型/参数、启动脚本和模块状态 |
| 数据与控制关系 | 当前状态从哪里来，目标由谁生成，怎样变成执行器输出 | 消息定义、发布/订阅位置、时间与坐标约定、算法输入输出 |
| 管理与保护关系 | 当前允许什么行为，什么时候拒绝、降级、切换或退出 | Commander/模式代码、控制启用标志、有效性检查、命令结果与事件 |

模块调用顺序与数据流方向不是同一回事。例如启动脚本可以先启动角速度控制，再启动位置控制；运行后两者通过消息交换数据，各自受调度和条件控制。

对后文十个阶段，使用同一套完成标准：

1. **解释**：面对具体场景，能预测哪些模块、接口和条件参与，以及结果可能怎样变化。
2. **定位**：能从入口追到实现，标出输入、输出、调度、参数和失败分支。
3. **修改**：能完成该阶段的一个独立任务，说明为什么改这里、影响哪些消费者。
4. **验证**：有正常与异常条件的证据；结果与预测不同时，能追到原因。
5. **迁移**：换一个类似模块或场景，仍能独立做完上述过程。

只完成前两项时记为“理解过”，做完具体任务但离开步骤无法复现时记为“跟做过”；能独立迁移时才记为该能力已掌握。仿真、真实板卡和其他机型分别记录验证范围。逐行背下所有驱动和算法既不现实，也不能替代工程验收；全局结构、关键机制与独立查证能力必须建立。

## 怎样使用这份路线

**每次只打开当前学习单元。** 第一课先跟随完整讲解建立读代码的方法；随后按单元问题阅读指定实现、完成实验、检查结果。实现细节通过链接进入开发指南；执行步骤通过链接进入操作手册。路线阶段按学习依赖排列，操作手册章节按主题排列，二者编号不要求相同。

一次集中学习可安排 2～3 小时：约 20 分钟复习问题与预测、40 分钟读实现、60 分钟实验、20 分钟解释结果。数学推导、环境准备和硬件实验可以拆成多次；这些是工作安排建议，不是完成期限。

每个单元达到三项要求才继续：**说得清机制、找得到实现、拿得出证据**。证据可以是带来源的关系图、手算结果、断点调用栈、测试断言或连续数据。编译成功、看过文件、截图中有曲线，不能单独替代相应能力。

每阶段在同一份个人学习记录中保留以下内容即可，不需要另建打卡系统：

```text
当前单元与问题：
预测及理由：
实现位置和关系：
输入条件、源码/参数身份：
操作与证据：
结论、适用范围、尚未解释的现象：
下一项任务：
```

<a id="lesson-1-2"></a>
### 1.2 展开第一课省略的构建选择过程

**问题**：`src/examples/work_item/` 中有代码，为什么 `make px4_sitl_default` 会包含它？

第一课已经认识目标配置和模块规则。这次沿它们之间的连接阅读：Kconfig 定义可选项，目标配置选择值，构建脚本把选择转换成参与构建的目录。

按顺序打开下面四处，每处只回答右侧问题：

| 顺序 | 源码入口 | 当前要找的内容 |
|---|---|---|
| 1 | [default.px4board](../boards/px4/sitl/default.px4board) | `CONFIG_EXAMPLES_WORK_ITEM=y`：当前目标启用示例 |
| 2 | [work_item/Kconfig](../src/examples/work_item/Kconfig) | 选项名、类型和默认值；默认关闭与目标显式启用的区别 |
| 3 | [work_item/CMakeLists.txt](../src/examples/work_item/CMakeLists.txt) | `MODULE`、`MAIN`、`SRCS`、`DEPENDS` 各自作用 |
| 4 | [kconfig.cmake](../cmake/kconfig.cmake)、[根 CMakeLists](../CMakeLists.txt) | 搜索 `CONFIG_EXAMPLES`、`config_module_list` 和 `add_subdirectory`，追到模块目录被纳入 |

用下面的搜索定位，不要求通读根构建脚本：

```bash
rg -n 'WORK_ITEM|MODULE|MAIN|SRCS|DEPENDS' boards/px4/sitl/default.px4board src/examples/work_item
rg -n 'CONFIG_EXAMPLES|config_module_list|add_subdirectory' cmake/kconfig.cmake CMakeLists.txt
```

**动手成果**：画出“目标配置 → Kconfig 解析 → 选中目录 → 模块源文件与库 → PX4”并标注文件。记录目录名 `work_item`、构建目标 `examples__work_item`、运行命令 `work_item_example`。

**验收**：解释为什么这三个名字不同；指出新增一个 `.cpp` 后，还需要核对什么才能让它进入编译。本单元只研究选择关系，不通过删改已有构建配置制造问题。

<a id="lesson-1-3"></a>
### 1.3 从构建结果反查真实编译输入

**问题**：怎样确认编译器实际处理了哪个文件、用了哪些路径和选项？

开始构建前，按[环境约定](OPERATIONS.md#environment)确认当前源码、工具链和挂载关系。这里主仓库提交决定代码身份，子模块记录锁定依赖提交，镜像提供工具链；三者各有自己的版本。`~/embedded-lab/bin/lab info px4-main` 用于查看任务信息。镜像标签不等于飞控源码版本，容器中的路径是 `/workspaces/PX4-Autopilot`。环境检查是为这次构建服务的，不是单独一门入门课。

先读开发指南 3.3～3.4，再按[构建操作](OPERATIONS.md#build-first)完成或确认一次构建。在宿主执行：

```bash
~/embedded-lab/bin/lab exec px4-main -- make px4_sitl_default -j2 PX4_MAKE_ARGS=-j2
ls -l build/px4_sitl_default/bin/px4
rg -n 'CMAKE_HOME_DIRECTORY|CMAKE_BUILD_TYPE' build/px4_sitl_default/CMakeCache.txt
rg -n -B 3 -A 2 'WorkItemExample.cpp' build/px4_sitl_default/compile_commands.json
```

每条检查通过后继续；编译数据库缺失时，先检查 CMake 的 `CMAKE_EXPORT_COMPILE_COMMANDS` 选项，不用编辑器手工添加一堆头文件路径。打开命中的完整 JSON 条目，圈出源文件、工作目录、编译器、宏、头文件路径和优化选项。容器中的绝对路径应与实际挂载一致。

再按[索引配置](OPERATIONS.md#editor-index)使用这份数据库，在编辑器跳转 `WorkItemExample::Run()`。将 `bin/px4`、生成头、`compile_commands.json`、`CMakeCache.txt`、`rootfs` 分别标为程序、接口产物、编译信息、配置缓存和运行目录。

**验收**：从编译数据库证明源文件参与了编译，并解释“编译成功但编辑器找不到头文件”的定位方法。这里还不能证明模块已经运行；该证据在下一单元取得。

<a id="lesson-1-4"></a>
### 1.4 用一次小改动打通源码到运行

**问题**：怎样证明实际运行的是这次修改过的代码？

1. 查看 [WorkItemExample.cpp](../src/examples/work_item/WorkItemExample.cpp) 的 `Run()`，找到教学消息 `data.val = 314159`。先记录该行原状；有自己的改动时逐项保留。
2. 仅把教学常量改为 `314160`，查看 `git diff -- src/examples/work_item/WorkItemExample.cpp`，使用 1.3 的命令增量构建。区分源文件重编、库更新和最终链接；其他依赖也可能触发构建，不要求固定步数。
3. 确认上一次使用同一运行目录的 SITL 已退出，再按[仿真与模块运行](OPERATIONS.md#module-runtime)启动 SIH，在 `pxh>` 分别执行下面命令。出现模块已启动等错误时先查状态，不继续猜测输出来源。

```text
work_item_example start
listener orb_test
work_item_example stop
shutdown
```

### 6.1 追踪一次起飞请求的生命周期

从 [Commander.cpp](../src/modules/commander/Commander.cpp) 的命令处理进入健康检查、解锁和模式管理，再到 [navigator/takeoff.cpp](../src/modules/navigator/takeoff.cpp)、[FlightTaskAuto](../src/modules/flight_mode_manager/tasks/Auto/FlightTaskAuto.cpp) 和位置控制。搜索命令常量与主题连接，跨模块部分用发布/订阅图表示。

记录请求、接受/拒绝、模式变化、目标形成、检测离地的不同证据。结合参数读取位置，解释默认起飞高度何时转化为本次目标。

**验收**：能说明命令接受为什么不等于动作完成，解锁为什么不等于离地；找到请求被拒绝时首先应查的条件。

<a id="lesson-6-2"></a>
### 6.2 规划并执行一项可验证任务

按[任务规划](OPERATIONS.md#mission-planning)先在纸上确定起点、两个观察点、停留、返回和降落，标注高度参考、速度与停止空间；按[QGC 操作](OPERATIONS.md#mission-qgc)上传、下载核对、执行。

沿 [mission.cpp](../src/modules/navigator/mission.cpp) 到任务目标与自动轨迹，记录任务项编号、期望轨迹和实际位置。把“任务项完成”“到达判定”“保持误差”分开解释。

**验收**：每一次任务推进都有对应条件和数据。QGC 无法连接时按[网络检查](OPERATIONS.md#qgc-tools)定位；不把无法显示地图当作飞控算法错误。

<a id="lesson-6-3"></a>
### 6.3 比较完成、取消和返回

按[模式交接实验](OPERATIONS.md#mission-transitions)对同一任务分别执行正常完成、途中切 Hold、再请求返回。每次先确定可执行条件，记录实际模式与目标交接。

再在条件相同的航线中单独改变巡航限制，比较预期目标与实际速度，承接 5.4。若航段太短未达到限速，使用运动约束解释结果，不继续无目的调参。

**验收**：能解释目标是谁生成的、模式切换后谁接管，以及返回点和返回高度怎样参与行为。不能只凭按钮点击认定接管成功。

<a id="lesson-6-4"></a>
### 6.4 用测试和地面仿真研究保护

先按[保护测试](OPERATIONS.md#failsafe-tests)阅读并运行 [failsafe_test.cpp](../src/modules/commander/failsafe/failsafe_test.cpp) 中一个位置或 Offboard 场景，记录初始模式、标志、延时、动作与恢复条件。

再按[GNSS 质量退化](OPERATIONS.md#gnss-degradation)在落地上锁的 SIH 中操作。先保存原参数，观察测量质量、状态有效性、预检与保护标志，再恢复并确认恢复。区分遥控丢失、地面站丢失和外部目标断流。

**阶段验收**：完成[第二次综合验收](#milestones)，用同时间轴解释一次任务和一种异常。地面检查变化只证明对应条件，空中保护结论需相应测试或仿真。下一步进入[阶段 7](#s7)。

## 阶段 7：通信协议与外部应用

**前提**：能解释模式条件和控制权。**阅读范围**：[通信原理](TECHNICAL.md#c10)、[Offboard 实现路径](DEVELOPMENT.md#d8)。先只读遥测，再请求控制，最后接其他消息通道。

<a id="lesson-7-1"></a>
### 7.1 理解遥测、命令、参数和任务的区别

入口：[mavlink_receiver.cpp](../src/modules/mavlink/mavlink_receiver.cpp)。从一个命令消息的解码追到 uORB 命令、处理者与 ACK；再对比一条状态遥测的来源。按[接口定义](OPERATIONS.md#external-contract)列 system/component 身份、端口、频率、超时和完成条件。

为命令、参数读写、任务上传分别画请求/响应过程。标明重试、重复请求和 ACK 超时与实际行为完成之间的关系。

**验收**：能区分消息送达、请求接受、行为完成三层；能判断通信故障属于地址、协议身份、消费者还是运行条件。

<a id="lesson-7-2"></a>
### 7.2 实现只读遥测并检查数据质量

按[只读遥测实践](OPERATIONS.md#telemetry-first)建立连接，只订阅 heartbeat、模式和位置，检查目标系统身份、实际消息频率、时间和有效性。记录一段连接、正常更新、暂停发送或断开、恢复的状态。

把程序输出与 PX4 内部消息对照，列出协议传输中发生的字段、单位和频率变化；不要默认网络端与内部主题完全等价。

**验收**：程序能够识别数据过期，并将“没有更新”与“值没有变化”分开；记录超时阈值的依据后进入控制实验。

<a id="lesson-7-3"></a>
### 7.3 实现有退出路径的 Offboard 应用

按[Offboard 实验](OPERATIONS.md#offboard-practice)先读示例与前置条件，再为应用写出等待可用、发送目标、请求模式、确认接管、运行、退出、故障七个状态。核对每个状态的输入条件和超时。

分别验证正常退出、请求拒绝、目标流停止和重新连接。确认 PX4 实际模式已交接，再结束正常目标流；断流测试按已明确的策略执行。示例只作为实验起点，最终应用需处理状态有效性、身份和参考变化。

**验收**：模式与目标数据能证明控制权交接；应用在失败时能结束当前流程并报告原因，而不是无限重复发送请求。

<a id="lesson-7-4"></a>
### 7.4 将相同理解迁移到 DDS/ROS 2

按[ROS 环境](OPERATIONS.md#ros-environment)核对 Client、Agent、消息定义与运行环境，再按[DDS 实践](OPERATIONS.md#dds-practice)读取一条状态消息。核对实际 topic 名称、类型、QoS 和坐标。

迁移上一单元的状态机时，分别处理 Offboard 控制信号和目标主题。比较 MAVLink 和 DDS 两条路径在序列化、主题选择、版本与权限条件上的差别。

**验收**：能定位“发现主题但无数据”，并解释更换通信通道为何不消除模式和状态有效性要求。依赖未准备完成时记录阻塞，不把该单元记作通过。

<a id="lesson-7-5"></a>
### 7.5 设计外部定位和载荷接口

按[外部定位与载荷](OPERATIONS.md#vision-payload)为视觉位置写数据契约，覆盖世界系、机体系、原点、时间、协方差、重定位和失联。用静止、单轴移动、旋转、短时中断、参考重置五种条件逐项验证；缺少实际输入源时先做契约与测试设计。

为相机请求建立“发送—接受—曝光—保存”状态，设计超时和重复请求处理。将曝光时刻与位姿关联，而不直接使用文件保存时刻。

**阶段验收**：形成一个有明确失败处理的外部应用，并解释外部观测、运动目标、载荷动作属于不同接口。后续在[阶段 8](#s8)集中完善定位与回归能力。

<a id="s8"></a>
## 阶段 8：故障定位、实时性能与回归验证

**前提**：已实际用过断点、日志和至少一种测试。**阅读范围**：[验证原理](TECHNICAL.md#c13)、[调试方法库](OPERATIONS.md#methods)。围绕一个故障组织方法，不把工具命令逐个运行一遍当作学习成果。

<a id="lesson-8-1"></a>
### 8.1 将一个现象变成最小复现

选择此前真实遇到的问题，写明预期、实际、触发条件和复现概率。若尚无案例，使用教学模块“参数读回正确但实际周期未变”的场景：在实验副本中漏掉调度更新调用，预测现象后再验证，最终恢复并增加行为检查。

按[定位组合方法](OPERATIONS.md#diagnostic-workflow)提出至少两个解释，例如运行旧程序、未收到更新、已收到但未应用。为每个解释选择能区分它的观察点，逐步缩小到实际代码位置。

**验收**：别人能按记录复现；根因有直接证据，且能排除一个看似合理的替代解释。整理可审查的修复，不把整个环境重建当作结论。

<a id="lesson-8-2"></a>
### 8.2 区分逻辑错误、崩溃与时序问题

对上个单元的逻辑问题使用断点和调用栈；再按[GDB 与崩溃分析](OPERATIONS.md#e2)学习符号、线程、core 与二进制匹配。没有崩溃样本时在独立教学程序或已有测试中研究，不破坏正常飞控来获取 core。

为“断点不命中”“变量 optimized out”“后台线程出错”“模式因暂停而超时”各写一个定位分支。编辑器调试与终端 GDB 使用同一源码和二进制身份。

**验收**：能说明哪些问题可以暂停观察，哪些需要持续日志和性能记录；能从栈找回源文件和实际调用路径。

<a id="lesson-8-3"></a>
### 8.3 测量运行代价并选择验证工具

按[性能分析](OPERATIONS.md#e5)为教学模块记录执行周期、耗时、发布频率和队列条件，区分仿真时间与墙上时间。每次只改变周期或计算量之一，比较负载变化，恢复后确认基线。

按[Sanitizer 与测试](OPERATIONS.md#e6)为相关单元测试启用适用检测，读报告中的第一个有效错误。覆盖率仅用于找未触达分支；日志回放用于相同测量下的重算，不能代替重新闭环运行。

**验收**：能解释工具开销、测量窗口和测试边界；零耗时计数或高覆盖率不能直接证明实时性能和行为正确。

<a id="lesson-8-4"></a>
### 8.4 为修复建立能长期运行的回归

先建立会暴露原问题的检查，再验证修复后的正常、边界、异常和恢复路径。按[测试筛选](OPERATIONS.md#test-tools)确认实际执行的用例，避免把“未找到测试”当作成功。

把相关仿真场景整理为可重复执行的过程：明确初始参数、实例、超时、成功/失败判据、日志位置和结束清理。固定输入条件，多次比较；不要求所有数值逐位相同，但容限要有依据。提交前审查源码差异、格式与受影响消费者，具体 Git 操作由开发者决定。

**阶段验收**：交付最小复现、根因、有限修复、回归和资源影响记录。能从记录恢复试验条件，再进入[阶段 9](#s9)。

## 阶段 9：硬件、操作系统与部署

**前提**：能分层定位软件问题。**阅读范围**：[硬件系统](TECHNICAL.md#c3)、[平台差异](DEVELOPMENT.md#d1)、[板级开发](DEVELOPMENT.md#d10)。实际操作需要确定板型、硬件资料及相应工具；没有设备时完成构建与静态分析，实测项保留为待完成。

<a id="lesson-9-1"></a>
### 9.1 从板卡身份建立资源图

按[板卡识别](OPERATIONS.md#board-identity)记录确切型号、硬件版本、处理器、存储、供电、IMU、通信总线和输出。找到对应 `boards/<vendor>/<board>/`；从配置、板级代码和原理图交叉核对资源，不能只按相似产品名选固件。

比较当前 SITL 与该板的工具链、平台、启用模块、设备来源和产物。为中断、DMA、定时器、串口和 CAN 标注用途，未知项记录待查依据。

**验收**：能指出一项外设或输出由哪些资源支持，并说明哪些资源配置错误会导致软件正常启动但设备不能工作。

<a id="lesson-9-2"></a>
### 9.2 追踪从复位到应用运行的启动链

按[固件构建](OPERATIONS.md#firmware-build)选择明确板型，区分 ELF、固件包和启动加载器。沿该板启动链、NuttX 初始化、[px4_init.cpp](../platforms/nuttx/src/px4/common/px4_init.cpp) 与[硬件 rcS](../ROMFS/px4fmu_common/init.d/rcS)解释设备和应用的启动顺序。

有板时保存原固件身份、参数和对应恢复方法，再按该设备文档进行加载与启动观察。用启动控制台区分引导、操作系统、设备和上层模块失败；网络 Shell 要在相应服务运行后才能工作。

**验收**：产物与板型匹配，有启动证据，并能解释早期启动故障应该从哪里观察。仅构建成功时记录为编译验证。

<a id="lesson-9-3"></a>
### 9.3 无桨台架验证设备、校准与输出

按[台架顺序](OPERATIONS.md#hardware-bench)验证供电、设备身份、方向、校准、RC 输入、参数持久化、输出功能映射与日志。逐项记录预期与观察，不因地面站显示连接就认定设备链已成立。

将阶段 3 的驱动图与实际总线、样本时间、错误计数对应；研究输出时确认无桨及设备测试条件，记录逻辑电机编号到物理通道的映射。把 SITL 中没有覆盖的振动、电气、时钟和执行时延列为单独变量。

**验收**：形成板卡与载具对应的配置和设备证据。实际飞行测试须另按机型、场地与操作条件组织；无桨台架结果不标为实飞性能结论。

<a id="lesson-9-4"></a>
### 9.4 完成一次板上定位或设备集成

按[板上调试](OPERATIONS.md#e8)研究对应设备的串口、SWD/GDB、栈和 HardFault 信息。选择一个明确设备状态或参数问题，验证定位方法；调试器暂停对外设和系统的影响需单独考虑。

有新设备需求时，依据[驱动开发](DEVELOPMENT.md#driver-development)实现探测、配置、采样、发布、异常恢复，再验证超时、错误输入和资源开销。无新设备时选择已有驱动的一项行为扩展，先写需求与测试条件。

**阶段验收**：能解释软件、总线、设备、安装与输出问题的不同证据。有硬件时交付一项实际部署/定位成果；无硬件时完成资料与构建分析，携带待验证项进入[阶段 10](#s10)。

<a id="s10"></a>
## 阶段 10：机型迁移与完整工程项目

**前提**：能独立使用前述方法；硬件能力按实际证据记录。**阅读范围**：[机型体系](TECHNICAL.md#c11)、[开发类型](DEVELOPMENT.md#d10)。本阶段要求自己选择修改层和验证方法，逐条照抄已有练习不足以通过。

<a id="lesson-10-1"></a>
### 10.1 比较固定翼、VTOL 与车辆的结构差异

按[机型比较](OPERATIONS.md#vehicle-transfer)先对照多旋翼、固定翼和 VTOL 的启动脚本及控制模块。分别解释固定翼空速/能量与侧向导引、VTOL 过渡、车辆转向与动力学约束。

做三个算例：固定翼给定速度与半径的转弯倾角、VTOL 过渡时可用执行器变化、车辆给定轴距与转角的曲率。然后选一种非四旋翼机型深入仿真，核对模型、参数和任务条件。

**验收**：形成共用机制与机型特有机制的对照表。可以复用消息和导航框架，不代表起飞、保持、返航与失效动作具有相同物理含义。

<a id="lesson-10-2"></a>
### 10.2 项目 A：完成可恢复的系统应用

需求：访问两个观察点并停留，允许中途取消，通信或状态条件不满足时退出至明确行为。使用阶段 7 的应用经验，自己确定采用任务协议还是外部目标，说明选择理由与控制权边界。

先写状态机、接口、约束和验收场景，再实现。按[应用项目](OPERATIONS.md#application-project)覆盖正常完成、启动条件不足、取消、断流和恢复。若加入相机，分开验证到达、请求接受和曝光/保存反馈。

**验收**：他人能按记录运行；每个业务完成结论都有相应设备或仿真证据。已有示例没有覆盖的条件由项目补齐。

<a id="lesson-10-3"></a>
### 10.3 项目 B：修改一项真实内部行为

从轨迹约束、输入有效性处理、设备恢复或其他明确需求中选一项。按[内部改动项目](OPERATIONS.md#internal-project)先说明现有实现为什么不满足需求，确定最小修改层与全部受影响消费者。

先复现，再写能暴露问题的测试或场景，实施修改，覆盖边界与恢复；最后验证仿真、配置兼容与运行代价。重大算法改动应先完成模型、可控测试和对照评价，不直接以一次起飞作为验证。

**验收**：需求、设计、差异、测试和结果可以对应审查。能说明为什么改这里、为什么没有破坏相邻行为，以及怎样恢复。

<a id="lesson-10-4"></a>
### 10.4 项目 C：部署或跨机型迁移

有硬件时，将一个有边界的成果部署到确定板卡，核对资源、设备与时序，完成阶段 9 的相应实测。具备实飞条件后，按任务和机型分步骤增加飞行验证。

无硬件时，在另一机型完成任务、取消和一种退化场景，分析目标含义、控制结构和保护条件。该项目证明软件迁移能力，硬件验证仍保留为未完成；两种成果不互相替代。

**验收**：能指出仿真和原机型的哪些结论可复用，哪些被新物理条件推翻，并给出新的验证依据。

<a id="lesson-10-5"></a>
### 10.5 从干净环境恢复，并处理一个新问题

按[项目交付](OPERATIONS.md#project-review)记录源码/依赖提交、工具版本、构建目标、运行机型、参数、输入、执行步骤和判据。在独立工作目录或隔离环境验证恢复，不删除现有成果来证明可复现。

让同伴复现，或隔一段时间仅凭记录自行复现。加入一个未逐条教过的问题，例如主题发现但没有数据、模式请求被拒绝或输出未达预期；先提出定位方案，再查看答案。

**阶段验收**：完成第三次综合验收，能够将方法迁移到新问题。后续按估计、控制、平台或自主应用深入，同时保持完整系统的影响分析。

## 三次综合验收：决定什么时候推进

| 时机 | 独立任务 | 通过依据 | 失败时返回 |
|---|---|---|---|
| 阶段 2 结束 | 给独立教学模块增加一个有意义的状态字段，完成构建、发布、记录与一次停止/重启分析 | 不靠逐行提示找到全部修改点，能区分未生成、未运行、未更新和未记录 | 构建回 1.2～1.3；执行回 2.1～2.2；数据回 2.3～2.6 |
| 阶段 6 结束 | 用一段完整任务的数据解释一次行为变化，排除目标、估计、控制中的至少一种替代解释 | 同一时间轴上有模式、目标、反馈与必要的输入/输出证据；能说明异常和恢复条件 | 数据语义回 3.1；重置回 4.4；跟踪回 5.4；模式回 6.1～6.4 |
| 阶段 10 结束 | 完成系统应用、内部改动与部署/迁移，恢复环境后处理一个新问题 | 需求有实现，异常有处理，修复有回归，记录可复现，硬件与仿真结论分清 | 按问题责任层回到相应单元，保留已经成立的证据 |

## 卡住时怎样继续

| 当前障碍 | 先做的具体工作 | 返回入口 |
|---|---|---|
| 不知道代码在哪里 | 从输入/输出主题和模块注册开始，先列生产者与消费者 | [模块地图](DEVELOPMENT.md#d7)、1.2、2.3 |
| 文件太长、读完没有印象 | 只追本单元列出的入口和状态变化，每个函数记录输入、条件和下一步 | [源码阅读方法](DEVELOPMENT.md#d12) |
| C++/任务概念不清 | 以 WorkItem 的构造、init、Run、退出画对象寿命和执行上下文 | 2.2 |
| 编译过了但行为没变 | 先对二进制、进程、配置和触发条件逐层取证 | 1.4、2.1、2.4 |
| 数学公式看不懂 | 缩到单轴、单步、已知数值，带单位计算，再回到矩阵或闭环 | 3.1、4.1、5.1 |
| 日志很多但不能解释 | 先写两个竞争解释，再选择能区分它们的最小主题集合与窗口 | 4.4、5.4、8.1 |
| 测试通过但没有信心 | 检查实际用例数，说明每个断言代表的行为，并验证一个旧错误会被捕获 | 4.3、5.5、8.4 |
| 没有硬件或外部设备 | 完成契约、代码和模型验证，列出具体缺失的设备证据 | 3.4、7.5、9、10.4 |

当一个单元尚有关键结论解释不了时，在记录中留下“预期—实际—证据—未解决点”，下一次继续处理它。完成当前单元后按顺序进入下一项；只有综合验收通过，才把相应能力标为已掌握。

# 二、系统学习路线

[学习入口](README.md) · [技术实现与架构](01-understand-px4.md) · [分阶段操作手册](03-practice-guide.md)

## 目标：形成独立工作的能力

“掌握 PX4”在这里指四种能力同时成立：解释完整飞行链；独立沿消息定位实现；完成有边界的功能修改；用测试、仿真、日志和适当的硬件验证判断结果。最终应能回答一个问题为什么属于估计、控制、模式、驱动或外部接口，而不是遇到异常只会换参数或重装环境。

先以 **v1.17.0 + SIH 四旋翼** 贯通主线。你已经跑过编译、起飞和降落，因此阶段 1 的环境动作只需确认；学习起点仍然是建立概念。完成四旋翼开发主线后，再扩展其他机型与真机。没有硬件时可先完成硬件源码与固件构建部分，台架和飞行部分要等实际设备具备后完成。

## 十个阶段的前后关系

| 阶段 | 要解决的核心问题 | 阅读 | 实验 |
|---|---|---|---|
| 1 认识系统与工程 | 当前有哪些程序，哪份代码在哪运行 | 架构 1～4 | [确认版本、依赖、构建与启动](03-practice-guide.md#s1) |
| 2 读懂一次飞行 | 一次起降中的数字与状态是什么意思 | 架构 3、5 | [观察完整闭环，追起飞高度](03-practice-guide.md#s2) |
| 3 进入开发 | 一个模块如何编入、运行、交换消息 | 架构 4、11.1 | [改造现有 WorkItem，增加参数](03-practice-guide.md#s3) |
| 4 理解测量 | 传感器原始值怎样变成算法输入 | 架构 6 | [追踪 IMU 两条处理链](03-practice-guide.md#s4) |
| 5 理解估计 | 状态从哪里来，为什么拒绝观测或重置 | 架构 7 | [手算更新，运行融合测试](03-practice-guide.md#s5) |
| 6 理解控制 | 目标怎样变成姿态、力矩和电机输出 | 架构 8、11.2 | [控制测试、起飞对照、日志分析](03-practice-guide.md#s6) |
| 7 理解行为与异常 | 模式为何变化，失效保护怎样选择动作 | 架构 9 | [GNSS 质量实验、失效测试](03-practice-guide.md#s7) |
| 8 连接外部系统 | 外部信息怎样进入飞控，并安全退出 | 架构 10 | [MAVLink、Offboard、DDS、Gazebo](03-practice-guide.md#s8) |
| 9 迁移机型和硬件 | 哪些机制共用，哪些必须重新验证 | 架构 12、13 | [机型比较、板级阅读、台架顺序](03-practice-guide.md#s9) |
| 10 独立开发与定位 | 能否自己完成可复现、可验证的修改 | 架构 11、13.3 | [完整开发案例与调试流程](03-practice-guide.md#s10) |

不要先把三篇全文背完再开始，也不要只复制命令。每阶段用相同顺序：**读对应原理 → 预测现象 → 做实验 → 回到源码解释结果**。一次实验只改变一个主要因素；遇到失败先按手册定位它属于哪一层，再继续。

## 阶段 1：认识 PX4，固定学习对象

**问题**：PX4、飞控板、QGC、SIH、Gazebo、Docker 是什么关系？你运行的究竟是哪个版本，子模块为什么不自行选最新版？

先连续读架构篇第 1～4 章。把你当前的系统画成五个框：宿主源码、开发容器、构建产物、运行中的飞控、虚拟飞机。给每个框写出具体路径或进程职责。然后检查主仓库基线、当前分支、子模块和 lab 的源码挂载位置。

按 [操作阶段 1](03-practice-guide.md#s1) 做一次增量编译并启动 SIH。重点观察“编译结束”和“飞控启动”是两个阶段；用启动日志找到 airframe ID 和实际启动脚本。

源码只读四处：[Makefile](../Makefile)、[default.px4board](../boards/px4/sitl/default.px4board)、[rcS](../ROMFS/px4fmu_common/init.d-posix/rcS)、[10040_sihsim_quadx](../ROMFS/px4fmu_common/init.d-posix/airframes/10040_sihsim_quadx)。先知道各自控制什么，无需逐行读完整个 Makefile。

**这一阶段学会的判断**：镜像版本不决定源码版本；构建成功不表示已经运行；没有图形窗口不表示没有仿真；文件夹存在不表示它被编译。你应能解释此前 CMake 路径错误和裸 `lab` 找不到命令的原因。

<a id="s2"></a>
## 阶段 2：把一次起降读成系统行为

**问题**：`Armed`、`Hold`、`landed` 分别描述什么？z 为什么是负值？飞机升高了多少？“默认起飞高度 2.5 m”在哪里变成控制目标？

读架构篇第 3、5 章，再按 [操作阶段 2](03-practice-guide.md#s2) 记录地面、上升、保持、落地四个时段的状态。把状态、位置、目标同时观察，不用单个截图推断完整飞行。

源码按“字段定义 → 发布处 → 使用处”读：`VehicleLocalPosition.msg` → `EKF2::PublishLocalPosition()` → 位置控制器读取它的位置；起飞高度按参数定义 → Navigator → FlightTaskAuto → trajectory_setpoint 追踪。

你的已有数据可以直接用作第一道分析：在参考连续的条件下，`-0.59442 - (-2.88696)=2.29254 m`。还要解释为什么它与 `dist_bottom=2.30908` 接近，却不应与 `-z` 混为一谈。

**这一阶段应能独立说明**：收到请求后，谁决定是否执行、谁生成目标、谁估计状态、谁闭环控制。发生“起飞没反应”时，能按链路选择下一条检查命令。

<a id="s3"></a>
## 阶段 3：读通工程机制，完成第一次源码修改

**问题**：代码如何进入 px4？模块什么时候被调度？发布/订阅如何工作？参数修改怎么到达运行对象？

读架构篇第 4 章及 11.1。按 [操作阶段 3](03-practice-guide.md#s3)，先运行上游已有的 `work_item_example`，确认它读解锁状态并发布 `orb_test`。然后把它改成定时的局部位置观察器，再添加一个参数控制报告频率。

这次实验选择已有模块，是为了把注意力放在调度、消息、有效性和参数上。不要同时做目录重命名、板卡移植和新消息定义。把 `CMakeLists.txt`、Kconfig、板级配置、入口函数和 `Run()` 的关系彻底读懂后，创建新模块只是按已理解的规则组织文件。

如 C++ 不熟，围绕实际用到的内容补：类与成员初始化、继承与 `override`、引用、模板类型、对象生命周期、RAII。比如 `uORB::Subscription` 是持有订阅状态的对象；`ModuleBase<WorkItemExample>` 为具体模块复用生命周期接口。先能解释这几个用法，不必先把整个语言标准学完。

**完成程度**：能编译改动，start/stop/start 不残留状态；正确区分没数据、旧数据、无效数据和正常数据；参数变动按预期影响报告频率；解释为什么 WorkItem 内不能无限循环和长时间睡眠。

<a id="s4"></a>
## 阶段 4：从设备到算法输入

**问题**：为什么 sensor_gyro、vehicle_imu、vehicle_angular_velocity 同时存在？校准、滤波、积分和偏置估计分别解决什么？

读架构篇第 6 章。先观察消息中的设备、实例、单位、采样时间，再阅读 BMI088 驱动状态机、通用陀螺仪封装、VehicleIMU 和 VehicleAngularVelocity。

按 [操作阶段 4](03-practice-guide.md#s4) 算一个 IMU 积分区间的平均角速度，再与控制使用的角速度比较数量级。不要要求两个不同时间、不同滤波与窗口的数据逐点相等。

针对“角速度偶尔尖峰”做一次纸面定位：原始数据是否也有尖峰？是否伴随设备错误或 FIFO 异常？过滤后才出现还是之前已有？时间戳是否跳变？选中设备是否改变？每个假设都对应一层，而不是直接改 EKF 噪声。

**完成程度**：能把一个设备的原始测量追到两个消费者，并解释为什么估计与控制需要不同处理；能清楚区分仿真观察能证明什么、真实总线还需验证什么。

<a id="s5"></a>
## 阶段 5：理解 EKF2 的更新和融合管理

**问题**：为什么需要预测与校正？为什么收到 GNSS 数据仍可能不融合？为什么有时位置跳变而速度没有对应变化？

读架构篇第 7 章，先手算标量更新。遇到矩阵时，补向量、矩阵乘法、旋转、方差和协方差的基本含义；推导应服务于理解状态、不确定性和观测关系。

按照 [操作阶段 5](03-practice-guide.md#s5)，先运行现成高度融合测试，再读 `baroRef` 等用例的设置、扰动、推进时间和断言。之后追一条 GNSS 高度路径，逐个找开始、继续、拒绝、停止和重置条件。

阅读顺序应是封装输入 → 算法状态机 → 对应融合函数 → 输出与重置报告。不要从生成的长矩阵表达式开始；先知道那次更新在什么条件下被调用，再研究数学细节。

**完成程度**：能给一个高度异常提出有区分力的检查：测量问题、时间问题、创新拒绝、参考切换或真实运动；知道改噪声参数影响什么，不能解决什么。

<a id="s6"></a>
## 阶段 6：从控制数学走到飞行日志

**问题**：一个位置目标如何变成四个电机输出？控制器跟不上，是内环、限制、估计还是目标本身的问题？

读架构篇第 8 章，顺序从内向外：RateControl → AttitudeControl → PositionControl → ControlAllocator。每次先看库的输入输出，再看模块怎样调用、更新参数、发布消息。

按 [操作阶段 6](03-practice-guide.md#s6) 运行已有测试，手算一轮角速度控制，再做两次不同起飞高度的 SIH 实验。只改 `MIS_TAKEOFF_ALT`，其余条件保持可比，并在结束后恢复原值。

开始正式使用 ULog：按同一时间轴比较目标高度、估计高度、速度、模式和 reset 计数。先解释为什么轨迹有上升过程，再判断跟踪误差和稳定段。不用“最终飞起来了”概括全部性能。

**完成程度**：能指出 P、I、D 和前馈各自使用什么数据；说明饱和如何影响积分；区分归一化力矩、逻辑电机推力与物理输出；找到误差最先出现的环节。

<a id="s7"></a>
## 阶段 7：理解飞行模式和故障后的行为

**问题**：谁决定自动起飞、Hold、降落、上锁？哪些估计是某个模式的前提？多种异常同时出现时谁决定最终动作？

读架构篇第 9 章。首先在正常起降中对照 intended mode、actual mode、arming 和 landed，再读健康检查、模式需求和 failsafe 选择。

按 [操作阶段 7](03-practice-guide.md#s7) 在地面 SIH 改变模拟 GNSS 卫星数，观察测量质量和融合的变化；恢复后再检查恢复过程。随后使用现有 failsafe 功能测试研究受控条件下的策略。地面观察不能直接证明空中失效行为。

选择一个测试用例，用自己的话写出“已有状态 + 新异常 + 当前意图 → 最终动作”。这能让你区分故障发现和策略执行。不要为了得到想要的现象随意关掉健康检查。

**完成程度**：能解释模式拒绝的原因，并追到具体检查；知道同一种传感器故障在不同估计、模式和参数下可能产生不同结果。

<a id="s8"></a>
## 阶段 8：把外部程序接入系统

**问题**：数据怎样离开 PX4，又怎样变成可执行目标？程序断开时会怎样？网络与消息结构问题怎样区分？

读架构篇第 10 章。[操作阶段 8](03-practice-guide.md#s8) 分成四个连续小实验：

1. **MAVLink 只读观察**：确认端口、身份和实际遥测，建立内外消息对应关系。
2. **SIH Offboard 保持**：用当前位置作目标，先建立持续目标流，再手动切入 Offboard；最后验证正常退出和断流保护。
3. **DDS/ROS 观察**：有独立 ROS 环境后，验证 Agent、主题版本和 QoS，再比较内部/外部同一位置状态。未具备 ROS 环境时保留此项，不影响已完成的 MAVLink 能力。
4. **Gazebo 集成**：先确认依赖、模型和无图形闭环，再接 GUI。比较它与 SIH 的接口和模型差别。

Offboard 实验采用已有 `pymavlink` 依赖，避免把“学外部控制”的前置条件变成重装整个 ROS。以后移植到 ROS，重新检查消息版本、坐标、时间、保活与退出即可。

**完成程度**：能够证明“客户端收到了数据”“飞控接受了模式”“目标确实生效”“断流后行为符合配置”这四件不同的事；出现问题时知道检查网络、协议还是状态机。

<a id="s9"></a>
## 阶段 9：扩展机型，补齐硬件认识

**问题**：哪些平台机制通用，哪些控制假设只适用于四旋翼？为什么换一块板不能只改编译名称？

读架构篇第 12、13 章。按 [操作阶段 9](03-practice-guide.md#s9) 比较多旋翼和固定翼启动文件，理解固定翼能量控制与侧向导引；然后追一个 VTOL 过渡状态和一个车辆运动约束。

硬件部分先选择一个具体板型阅读配置、初始化、总线和输出定义。实际设备尚未确定时，可以做对应固件的构建练习，但不要把构建成功等同于适合现有设备。

设备具备后做无桨台架：确认启动、传感器方向与实例、通信、执行器映射、资源和日志。带载和飞行前，还需要正确装配、校准、动力检查和现场条件。它们属于硬件能力的一部分，不能用 SITL 替代。

**完成程度**：能解释至少一种其他机型为什么不能套用四旋翼的目标和控制；能把传感器或输出问题沿板级资源定位；如尚无设备，应明确哪些硬件结论仍未验证。

## 阶段 10：完成一项可以独立交付的开发

**问题**：没有现成逐条命令时，能否从需求到源码、测试、仿真和结论完整走一遍？

推荐题目是：**把阶段 3 的观察器改成能正确报告相对高度和数据健康的模块。** 它不改变飞行控制，却迫使你处理时间、有效性、参考重置、参数、生命周期和验证，范围足够小，系统联系足够完整。

按 [操作阶段 10](03-practice-guide.md#s10) 定义行为：

- 首次获得有效位置时建立参考；无数据或无效数据时不建立参考。
- 正常连续数据输出相对高度；参考重置时明确重建参考或按已定义策略补偿。
- 停止更新超过阈值时报告 stale，恢复后正确退出 stale。
- 重启模块重新建立会话状态；输出频率有上限。

把数据判断尽量抽成不依赖真实时钟的函数，用显式时间输入测试边界。然后编译模块，在 SIH 中做起降，比较观察器结果与日志。保留一个正常场景和几个异常场景的结果，提交代码及简明的行为说明。

之后可以选择控制库边界测试、已复现的小问题修复、设备驱动或外部接口作为下一项项目。始终先定义输入和预期，再决定应在哪一层修改。

**判断是否达到这条路线的目标**：别人给你一段异常日志或一个新需求，你能画出受影响的数据路径，指出该读的几个文件，设计能区分原因的实验，完成修改并解释证据与适用范围。对其他专题的深入仍会继续，但此时已具备系统学习和独立开发 PX4 的方法与基础。

## 每次学习结束时留下什么

不需要额外的管理系统。最有价值的记录只有四项：你解决的问题、关键源码位置、实际观测、由证据支持的结论。代码修改用独立 Git 提交保存；ULog 留本地，必要时提交小型分析结果。日常保存与恢复见 [操作手册的 Git 部分](03-practice-guide.md#git)。

如果一段学习记录只有“运行了某命令，成功”，还缺少技术解释；如果只有“原理应该如此”，还缺少实验。把二者接起来，就是这条路线要求的深度。
